# RB-6: Suspected secret leak or account compromise

**Alarms / signals:** `AuthFailureSpike` (SEV-3); a gitleaks finding; a secret seen in logs, a screenshot, an issue or a chat; unexpected CloudTrail activity; a report from a user or researcher ([SECURITY.md](../../SECURITY.md)).
**Owner:** operator. **Related:** [05 §2, §8, §9](../05-security-reliability.md#8-secrets-management), [ADR-006](../adr/0006-google-oidc-with-server-side-sessions.md), [ADR-010](../adr/0010-lambdas-outside-vpc.md), [privacy policy](../privacy.md).

Conventions are in the [runbooks README](README.md#conventions-used-in-the-runbooks).

## Symptoms

- `AuthFailures` > 50 in 10 minutes: token-validation failures, CSRF rejections, or invalid sessions in bulk.
- A secret value appears somewhere it should not (git history, logs, a pasted error).
- Sessions or commutes changed that the user did not change; logins from unexpected IP prefixes in the audit log.
- AWS activity nobody performed (CloudTrail), or GitHub Actions runs nobody triggered.

## Impact

Depends on the secret ([contracts §1](../contracts.md#ssm-parameters-securestring-under-ssm_prefix)):

| Secret (`/stopwatch/<env>/…`) | What an attacker could do |
|---|---|
| `database_url` (app role) | Read and modify all user data from anywhere: Lambdas run outside a VPC and Neon is internet-reachable ([ADR-010](../adr/0010-lambdas-outside-vpc.md)). **Treat as SEV-2.** |
| `database_owner_url` | All of the above plus DDL and audit-log deletion. **SEV-2.** |
| `session_secret` | Forge signed cookies (OIDC transaction, CSRF); if it peppers session hashes, attack sessions. **SEV-2.** |
| `google_client_secret` | Impersonate the app in Google's OAuth flow (phishing). SEV-2. |
| `vapid_private_key` | Send push messages to subscribed browsers. SEV-3. |
| `groq_api_key` | Spend or free-plan quota on the Groq account. SEV-3 (plus a cost incident, [RB-5](RB-5-cost-spike-abuse.md)). |
| `origin_verify_secret` (the `X-Origin-Verify` value) | Call the API directly, bypassing CloudFront, and forge `CloudFront-Viewer-Address` to evade per-IP rate limits (demo creation, login). No data access by itself. SEV-3. |
| AWS operator credentials or the GitHub deploy role | Everything. **SEV-2**; follow AWS's compromised-credentials guidance as well. |

## Severity

SEV-2 for anything that exposes user data or AWS control (see table). A credible leak is handled as confirmed until proven otherwise.

## Diagnose (briefly; containment comes first)

1. **Scope:** which secret, which environment, since when (the exposure window starts at the earliest time the value could have been seen).
2. **Audit log** (owner role, read-only):

   ```sql
   select at, actor_kind, actor_user_id, action, outcome, ip_prefix, request_id
   from audit_log
   where at > '<window start>'
     and action in ('auth.login','auth.login_failed','account.export','account.delete',
                    'commute.update','commute.delete','auth.logout_all')
   order by at desc limit 200;
   ```

3. **Auth-failure pattern** (`/aws/lambda/stopwatch-prod-api`):

   ```text
   fields @timestamp, message, error_type, request_id
   | filter error_type like /Auth|Csrf|Token|Nonce/
   | stats count(*) as n by error_type, bin(5m)
   ```

   Many failures from few IP prefixes with no successes is usually noise or credential probing (consider [RB-5](RB-5-cost-spike-abuse.md) throttling). Successes from unknown prefixes are the worrying case.

4. **AWS activity** (CloudTrail event history, 90 days, free):

   ```bash
   aws cloudtrail lookup-events --start-time <window start> \
     --lookup-attributes AttributeKey=EventSource,AttributeValue=ssm.amazonaws.com \
     --query 'Events[].[EventTime,EventName,Username]' --output table
   ```

   Repeat with `iam.amazonaws.com`, `lambda.amazonaws.com` and `sts.amazonaws.com`.

## Mitigate

Order: **rotate → force new containers → revoke sessions → review → notify.**

1. **Rotate the secret** at its source, then store the new value in SSM without putting it in shell history:

   ```bash
   read -rs NEWVAL && aws ssm put-parameter --name /stopwatch/prod/<name> \
     --type SecureString --overwrite --value "$NEWVAL"; unset NEWVAL
   ```

   | Secret | Rotate at the source |
   |---|---|
   | `database_url` / `database_owner_url` | Neon console → Roles → reset the password for `stopwatch_app` / `stopwatch_owner`; build the new URL (keep `sslmode=verify-full`) |
   | `google_client_secret` | Google Cloud console → APIs & Services → Credentials → the OAuth client → reset secret |
   | `session_secret` | Generate: `python -c "import secrets;print(secrets.token_urlsafe(48))"` |
   | `vapid_*` | Generate a new key pair; existing push subscriptions must re-subscribe |
   | `groq_api_key` | Revoke and create a new key in the Groq console; keep the spend cap |
| `origin_verify_secret` | Generated by Terraform (the documented exception to "no secrets in state"), so rotate it there, not with `put-parameter`: find the generating resource with `terraform -chdir=infra/envs/prod state list \| grep -i origin`, then `terraform -chdir=infra/envs/prod apply -replace=<address>`. One apply updates both CloudFront's header and the SSM parameter; then force new API containers (step 2). Until the API restarts, requests carrying the new value get `403` |

2. **Force new containers.** Secrets are read once per cold start and `live` points at an immutable version, so updating SSM alone leaves warm containers on the old value. Re-run the deploy workflow for the current commit (publishes new versions and moves `live` for every function), or `make up ENV=prod` if a configuration change is pending anyway.

3. **Revoke sessions** if the session secret or the database was exposed, or accounts look compromised (every user must sign in again):

   ```sql
   delete from sessions;                                   -- everyone
   delete from sessions where user_id = '<uuid>';          -- one user
   ```

4. **Leaked in git:** rotate first (history rewriting does not un-leak a pushed secret), then remove it from history if the repository is public, and confirm `gitleaks detect` on the full history is clean.

5. **Review** the audit log and CloudTrail for the whole exposure window; list affected users and actions.

6. **Notify** affected users without undue delay if their personal data (email, saved commutes) was likely accessed, as the [privacy policy](../privacy.md) commits to. Record the notification in the incident notes.

## Verify

- The old value no longer works (for the database: a connection with the old password fails).
- All functions run a version published after the rotation:

  ```bash
  for fn in api ingest-tick schedule-import daily-rollup maintenance notify lamp-validate; do
    aws lambda get-alias --function-name stopwatch-prod-$fn --name live --query FunctionVersion --output text
  done
  ```

- Sign-in, demo sign-in and commute saving work end to end; `AuthFailures` back to its baseline.

## Follow up

- Postmortem (SEV-2): how the secret leaked and what control would have stopped it.
- Record the rotation date; long-lived secrets are rotated quarterly anyway ([06 §11](../06-quality-operations.md#11-operating-cadence)).
- If Google, Neon or AWS account security was involved, review MFA and access for those accounts.
