# ADR-005: API Gateway HTTP API in front of the API Lambda, instead of a Lambda Function URL

- **Status:** Accepted, 2026-10-18
- **Deciders:** project author
- **Related:** [04 §2, §8.2](../04-architecture.md#8-interfaces), [05 §7](../05-security-reliability.md#7-rate-limiting-and-abuse), [contracts §4](../contracts.md#4-dynamic-api-apiv1), [RB-5](../runbooks/RB-5-cost-spike-abuse.md)

## Context

The dynamic API (`/api/v1`: sign-in, demo accounts, saved commutes, export/delete, should-tier Ask and push) runs in the `api` Lambda (FastAPI + Mangum). It sits behind CloudFront so that the SPA, the published data and the API share **one origin**: no CORS configuration, first-party `__Host-` cookies, and SameSite=Lax doing real work against CSRF ([05 §2](../05-security-reliability.md#2-authentication)).

The API is the main abuse surface of an otherwise static site: demo-account creation, login callbacks and (later) Ask all cost money or database time. Expected volume is small, about 10k requests a month.

| Option | Price | Throttling | Notes |
|---|---|---|---|
| **API Gateway HTTP API** | $1.00 per million requests (≈ $0.01/month here) | Stage and per-route rate/burst limits | Native Lambda proxy integration, access logs, CloudWatch 4xx/5xx/latency metrics |
| Lambda Function URL | free | none (only Lambda reserved concurrency) | As a CloudFront origin with Origin Access Control, `POST`/`PUT` bodies must be signed with a payload hash the browser has to compute |
| API Gateway REST API | $3.50 per million | yes, plus usage plans and API keys | Features (usage plans, request validation, WAF integration) not needed in the MVP |
| Application Load Balancer | ≈ $16+/month | no | Hourly billing |

## Decision

- Route CloudFront `/api/*` to an **API Gateway HTTP API** with a Lambda proxy integration on `/api/{proxy+}`.
- Throttle at the gateway: **20 rps steady / 40 burst** on the stage, **5 rps** on `/api/v1/auth/*` ([05 §7](../05-security-reliability.md#7-rate-limiting-and-abuse)).
- Keep **application-level** fixed-window limits in Postgres (`rate_limit_counters`) for per-user and per-IP-prefix quotas, for example `POST /auth/demo` at 3/hour/IP and 500 active demo users ([04 §8.2](../04-architecture.md#8-interfaces)).
- Cap the blast radius with `api` reserved concurrency 10.
- **Edge trust** ([05 §2](../05-security-reliability.md#2-authentication)): an HTTP API cannot be network-restricted to CloudFront, so CloudFront adds a shared secret header, `X-Origin-Verify`, to every `/api/*` origin request, and in staging/prod the API rejects requests without it (`403`). Because every accepted request has come through CloudFront, the client IP for rate limits is taken only from `CloudFront-Viewer-Address` (set by CloudFront from the TCP connection); `X-Forwarded-For` is never trusted.
- Use API Gateway's built-in metrics for the `Api5xx`, `ApiLatencyP95` alarms and the API dashboard.

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| **Lambda Function URL** behind CloudFront | Free, but there is no request throttling in front of the function, so every abusive request reaches Lambda and possibly Neon. Signing `POST` bodies for OAC pushes AWS-specific logic into the SPA; leaving the URL public instead exposes a second, unthrottled entry point that bypasses CloudFront. |
| **REST API** | 3.5× the price for features (usage plans, API keys) that are only a *could* item. Can be adopted later if public API keys ship. |
| **ALB** | Hourly cost; no throttling. |
| **No gateway; rate-limit in the app only** | Rejected requests would still cost a Lambda invocation and a database round trip; the gateway rejects floods before any compute runs. |

## Consequences

**Positive**

- Throttling and per-route limits without writing code, for about a cent a month.
- Same-origin routing stays simple: CloudFront has one behavior for `/api/*`.
- Free, standard metrics and access logs feed the alarms in [06 §9](../06-quality-operations.md#9-alerts).
- Emergency controls are a single CLI call: tighten stage throttles, or set them to zero as a last resort ([RB-5](../runbooks/RB-5-cost-spike-abuse.md)).

**Negative**

- One more hop (CloudFront → API Gateway → Lambda) adds a few milliseconds and one more component to configure in Terraform.
- The `execute-api` URL stays publicly resolvable; only the `X-Origin-Verify` check closes it. That secret is generated by Terraform and therefore sits in Terraform state, a documented exception to "no secrets in state" ([ADR-007](0007-terraform-over-cdk.md)): it grants no data access, it only proves a request came through CloudFront. If it leaks, an attacker can skip CloudFront and forge `CloudFront-Viewer-Address` to dodge per-IP limits until it is rotated ([RB-6](../runbooks/RB-6-secret-leak.md)).
- HTTP API has a 30-second integration timeout; fine for a 15-second Lambda timeout, but it rules out long-running requests.
- Gateway throttles are coarse (per stage or route, not per user), so per-user fairness still depends on the application's counters.

## Revisit when

- Public API keys with quotas (a *could* item) ship: REST API usage plans or a key check in the app become relevant.
- Sustained traffic exceeds ~50 req/s, or AWS WAF is needed for bot management (WAF attaches to CloudFront either way).
